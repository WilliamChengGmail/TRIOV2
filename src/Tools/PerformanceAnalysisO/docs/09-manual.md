## 1. 工具簡介

TRIOV2 效能分析器用於檢視 TRIOV2 模擬器／記錄器產出的硬體效能數據，協助：

- 查看每次監測的 CPU、記憶體、磁碟、網路、辨識表現
- 比較同一台機器多次測試的差異
- 比較不同機器的表現
- 找出異常（高負載、記憶體成長、任務重啟、資料缺損）
- 匯出單一 HTML 報告供閱讀與分享

原則：

- **唯讀**：不會修改原始 Logs
- **容錯**：缺檔、壞列、重複時間戳記都能繼續分析
- **離線**：所有功能不依賴網路
- **可解釋**：每個數字與警告都能回溯到原始樣本

## 2. 快速開始

### 已發佈版本

```text
publish\TRIOV2.PerformanceAnalysis.exe
```

雙擊啟動。

### 從原始碼

```powershell
cd D:\TRIOV2\src\Tools\PerformanceAnalysisO
dotnet run --project src\PerformanceAnalysis.App
```

### 載入資料

啟動後會自動載入：

```text
D:\TRIOV2\publish_tools\Logs
```

也可以：

- 在頂部路徑欄輸入資料夾後按 Enter 或「掃描」
- 按「瀏覽」選擇資料夾
- 把資料夾直接拖進視窗

行為：

| 選擇的資料夾 | 結果 |
|---|---|
| 單一場次（含 `System_BenchmarkLog.csv`） | 直接進入單場次分析 |
| 上層資料夾（含多個場次） | 進入總覽 |
| `裝置\場次` 巢狀結構 | 掃描時自動辨識裝置層 |

## 4. 各頁面功能

### 4.1 總覽

- **KPI**：檢測場次、裝置數量、任務種類、需要注意
- **歷次 CPU 趨勢**：各場次的 CPU 平均／最高
- **檢測紀錄表**：每場的 CPU／RAM／Δ 值／任務／警告／基準
- **任務覆蓋矩陣**：場次 × 任務，顯示各任務 CPU 平均
- **資料品質**：警告與錯誤摘要

操作：雙擊表格列進入單場次；表頭可排序；「列表／任務覆蓋矩陣」分頁切換。

### 4.2 單場次

由上到下：

1. 標頭：裝置、硬體、OS、時間範圍、樣本數、模式、基準狀態
2. KPI：CPU、RAM、磁碟、網路、辨識、資料完整率
3. 系統 CPU／記憶體圖
4. 任務執行時間軸（Gantt）
5. 任務 CPU／記憶體圖
6. 任務統計表
7. 備註與標籤
8. 診斷與資料品質
9. 原始資料（可展開）

操作：滑鼠滾輪捲頁；`Ctrl` + 滾輪縮放圖表；「開啟資料夾」開啟原始檔案；「設為基準」設為同裝置基準。

### 4.3 裝置

- 左側裝置列表（名稱／場次數／基準）
- 右側該裝置的場次
- 可編輯別名、設定基準、移動場次（合併）、拆分為新裝置

### 4.4 比較

- **同機多次比較**：勾選同一裝置的多場，選擇基準，看 Δ 值與疊圖
- **跨機比較**：每台裝置選一場，比硬體與 KPI
- 疊圖可切換：全系統 CPU／已用記憶體／模擬器 CPU

### 4.5 設定

- 異常門檻（見 [第 11 章](#11-設定與門檻)）
- 解析快取狀態與清除

## 5. 圖表與數據意義

### 5.1 系統 CPU 圖

```
Y 軸：使用率（%），0–100
X 軸：場次開始後的經過時間（分:秒）
```

| 線條 | 意義 | 顏色 |
|---|---|---|
| 全系統 | 整台機器的 CPU 使用率 | 藍 |
| 模擬器 | 模擬器程序的 CPU 使用率 | 青 |
| 閒置 | 剩餘空閒 CPU | 灰 |

判讀重點：

- **全系統接近 100%**：機器已滿載，其他程式可能被排擠
- **模擬器佔比高**：負載來自模擬器本身
- **出現尖峰**：某秒發生短暫重活（如辨識運算）
- **長時間維持高位**：持續高負載，見 `CPU_HIGH_SUSTAINED` 診斷

> 資料每秒一筆；同一秒重複的樣本在圖表上取平均。

### 5.2 記憶體圖

```
Y 軸：容量（GB）
```

| 線條 | 意義 | 顏色 |
|---|---|---|
| 已用 | 系統已使用的 RAM | 紫 |
| 可用 | 尚未使用的 RAM | 綠 |

判讀重點：

- **已用持續上升**：記憶體可能沒有釋放（見 `MEMORY_GROWTH` 診斷）
- **可用持續偏低**：機器接近記憶體上限（見 `RAM_HIGH` 診斷）
- 兩線合計約等於總記憶體（例如 16 GB）

### 5.3 任務 CPU／記憶體圖

- 每個任務一條線，圖例即任務名稱
- **只畫「執行中」的樣本**；任務未執行時不會出現
- CPU 單位 %；記憶體單位 MB

判讀重點：

- **某任務 CPU 高**：此任務吃資源
- **記憶體線下降再上升**：任務可能重啟過（對照 Gantt 與「重啟」欄位）

### 5.4 任務執行時間軸（Gantt）

- 每一列 = 一個任務
- 每一段色塊 = 一次連續執行
- 空白 = 未執行
- 顏色與任務圖表、任務統計表一致

判讀重點：

- **多段色塊**：任務多次啟動／重啟（PID 改變）
- **整列空白**：任務全程未執行（見 `TASK_NEVER_RUN`）

區間切分規則：

- 連續「執行中」且 PID 相同 → 同一區間
- 中斷超過 2 秒 → 切開
- PID 改變 → 切開（視為重啟）

### 5.5 歷次趨勢圖（總覽）

- X 軸：各場次的開始時間
- 線條：CPU 平均／最高（或 RAM 平均／最高）

判讀重點：

- 平均與最高**差距大**：負載不穩定（有尖峰）
- 整體往上走：後續測試越來越吃資源

### 5.6 比較疊圖

- 每條線 = 一個被選取的場次
- X 軸：各場次開始後的經過時間（對齊比較）

判讀重點：

- 同樣的開始時間點，不同場次的 CPU／RAM 高低差異
- 可用圖表下方的縮放條放大局部

### 5.7 任務覆蓋矩陣

| 顯示 | 意義 |
|---|---|
| `23.8%`（青色底） | 該任務在該場次有執行，數字為 CPU 平均 |
| `未執行`（灰底） | 該場次有此任務，但全程未執行 |
| `—` | 該場次沒有此任務的紀錄 |

### 5.8 KPI 卡

| 卡片 | 主數字 | 附註 |
|---|---|---|
| CPU 平均 | 平均使用率 % | 最高、p95 |
| RAM 平均 | 平均使用量 GB | 最高、使用率峰值 |
| 磁碟峰值 | 任務最高 I/O | 總量 MB |
| 網路峰值 | 任務最高頻寬 | 總量 MB |
| 辨識時長 | 平均 ms | 最高、p95 |
| 資料完整率 | % | 樣本數／預期樣本數 |

## 6. 統計指標定義

| 指標 | 定義 |
|---|---|
| 場次開始／結束 | 第一筆／最後一筆有效樣本的時間 |
| 場次時長 | 結束 − 開始 |
| 預期樣本數 | `round(時長秒數) + 1` |
| 資料完整率 | 不重複時間戳記 ÷ 預期樣本數（0–100%） |
| 平均 | 所有原始樣本的算術平均 |
| p50（中位數） | 一半樣本低於此值 |
| p95 | 95% 的樣本低於此值；比「最高」更能代表常態負載 |
| 最高／最低 | 峰值與谷值 |
| 標準差 | 離散程度；越大代表越不穩定 |
| CPU 秒數 | 任務累計的 CPU 使用量：每秒 CPU% ÷ 100 加總 |
| 執行率 | 任務執行時間 ÷ 場次時長 |
| 記憶體成長率 | 對「執行中」樣本做最小平方法，單位 MB/min |
| 磁碟／網路總量 | 每秒速率的加總換算（MB） |
| 重啟次數 | 執行區間數 − 1 |
| 狀態翻跳 | 執行中 ↔ 未執行 的切換次數 |

判讀提示：

- **平均**適合看整體水準
- **p95**適合看「大部分時間糟不糟」
- **最高**適合找尖峰
- 三種一起看，才不會被單一數值誤導

## 7. 診斷與判定依據

所有警告都有**明確的判定條件**；門檻可在「設定」頁調整。

### 7.1 資料缺損與格式

| 代碼 | 等級 | 判定依據 | 意義 |
|---|---|---|---|
| `NO_REF` | 警告 | 缺少 `ref.txt` | 硬體／OS 資訊可能不完整 |
| `NO_SYSTEM_LOG` | 警告 | 缺少 `System_BenchmarkLog.csv` | 只能用任務資料推估 |
| `NO_TASK_LOGS` | 警告 | 沒有任務 CSV | 只有系統資源，無任務明細 |
| `NO_SAMPLES` | 錯誤 | 完全沒有有效樣本 | 場次無法分析 |
| `PATH_NOT_FOUND` | 錯誤 | 掃描路徑不存在 | 請檢查路徑 |
| `NO_SESSIONS_FOUND` | 警告 | 找不到任何場次 | 資料夾結構不對 |
| `CSV_READ_FAILED` | 錯誤 | 檔案讀取失敗 | 權限或編碼問題 |
| `CSV_EMPTY` | 錯誤 | 沒有資料列 | 檔案內容為空 |
| `MISSING_TIMESTAMP` | 錯誤 | 找不到時間戳記欄位 | 版本不符 |
| `MISSING_COLUMN` | 警告 | 缺少預期欄位 | 該欄位以 0 處理 |
| `INVALID_ROWS` | 警告 | 時間戳記無效而略過 | 有 N 行無法解析 |
| `CSV_MALFORMED` | 警告 | 欄位數與表頭不一致 | 已補齊／截斷 |
| `CSV_COMMENTS` | 資訊 | 略過檔尾摘要列 | 正常現象 |

### 7.2 資料品質（門檻可設定）

| 代碼 | 判定依據 | 預設門檻 | 意義與建議 |
|---|---|---|---|
| `SHORT_SESSION` | 時長 < 門檻 | **10 秒** | 樣本太少，統計僅供參考 |
| `SAMPLE_GAP` | 相鄰樣本間隔 > 門檻 | **2 秒** | 記錄器中斷；該段時間沒有數據 |
| `DUPLICATE_TIMESTAMPS` | 同秒重複比例 > 門檻 | **1%** | 記錄器重複寫入；圖表取平均、統計用原始樣本 |
| `REF_MISMATCH` | 與 `ref.txt` 摘要差異 > 容忍度 | CPU 2%、RAM 2% | 檔案版本或解析不一致 |
| `METADATA_MISSING` | 沒有 `session.json` | — | 裝置資訊由 ref／CSV 推斷 |
| `METADATA_WRITE_FAILED` | 中繼資料寫入失敗 | — | 檢查資料夾權限 |

### 7.3 效能門檻（門檻可設定）

| 代碼 | 判定依據 | 預設門檻 | 意義與建議 |
|---|---|---|---|
| `CPU_HIGH_SUSTAINED` | CPU 連續 ≥ 門檻達指定秒數 | **≥ 90% 且 ≥ 10 秒** | 持續滿載；檢查是否有程式卡住 |
| `RAM_HIGH` | 使用率 ≥ 門檻，或可用 < 下限 | **≥ 90% 或 < 1 GB** | 記憶體壓力；可能觸發分頁 |
| `MEMORY_GROWTH` | 成長率 > 門檻，且時長 ≥ 觀察秒數 | **> 20 MB/min 且 ≥ 300 秒** | 疑似記憶體未釋放（漏洩傾向） |
| `TASK_RESTARTS` | 同一任務重啟次數 > 門檻 | **> 3 次** | 任務不穩定；查原因 |
| `TASK_NEVER_RUN` | 選了但全程「尚未執行」 | — | 啟動失敗或設定問題 |
| `UNKNOWN_STATE` | 狀態值無法識別 | — | 記錄器版本較新 |

### 7.4 判定原則

- 門檻是**提示**，不是好壞定論：請搭配圖表人工判斷
- 短場次（< 觀察秒數）**不會**判斷記憶體成長，避免誤報
- 重複樣本在圖表與統計採不同策略，診斷會明確寫出

## 8. 基準與 Δ 值

### 8.1 兩種基準

| 基準 | 範圍 | 設定位置 |
|---|---|---|
| **裝置基準** | 每台裝置一個 | 單場次「設為基準」、裝置頁 |
| **比較基準** | 比較頁自選 | 比較頁「基準」下拉 |

### 8.2 Δ 值怎麼看

Δ = 目前場次 − 基準場次：

| 例子 | 意義 |
|---|---|
| `ΔCPU +5.0%` | 比基準多用 5% CPU |
| `ΔRAM −1.20 GB` | 比基準少用 1.20 GB 記憶體 |
| `Δ辨識 +50 ms` | 辨識比基準慢 50 ms |
| `基準` | 此列就是基準本身 |
| `—` | 沒有可比較的基準 |

### 8.3 顏色規則

- **紅色**：變高（CPU、RAM、辨識變高＝變差）
- **綠色**：變低（變好）
- **灰色**：沒有差異或沒有基準

> 資料完整率相反：變高是綠色（完整率越高越好）。

## 9. 裝置識別

### 9.1 裝置怎麼認

優先順序：

1. `session.json` 的 `deviceId`／`deviceName`
2. `ref.txt` 的「裝置名稱」＋硬體
3. 資料夾結構（`Logs\<裝置>\<場次>`）
4. 否則視為「未識別裝置」

### 9.2 未識別裝置

顯示：

```text
未識別裝置 (2715)
```

括號內四碼是**裝置指紋後綴**，用來區分不同未識別機器。

### 9.3 建議做法

- 在「裝置」頁為未識別裝置輸入**別名**
- 把誤歸類的場次**移動**到正確裝置
- 必要時**拆分**成新裝置
- 移動／拆分會寫入 `deviceOverridden`，之後以中繼資料為準，不會被 `ref.txt` 拉回

位置：`<執行檔>\Metadata\settings.json`

| CPU 高負載門檻 | 90% | `CPU_HIGH_SUSTAINED` |

| 記憶體使用率門檻 | 90% | `RAM_HIGH` |

| 記憶體觀察秒數 | 300 | `MEMORY_GROWTH` |
| 短場次門檻 | 10 秒 | `SHORT_SESSION` |
| 跳秒門檻 | 2 秒 | `SAMPLE_GAP` |
| 重複樣本比例 | 1% | `DUPLICATE_TIMESTAMPS` |

- CLI 會讀取同一份設定
- 「回復預設」只帶入預設值，仍需儲存

## 12. 解析快取

- 已解析的場次暫存於**記憶體**
- key = 來源 CSV／`ref.txt` 檔名＋大小＋修改時間的 SHA-256
- 來源變更自動失效；改別名／基準／設定會主動清除
- 設定頁可查看數量與清除
- 關閉程式自動清除；**不會影響中繼資料**

## 16. 常見問題

### 為什麼任務 CPU 加起來可能超過全系統？

取樣時點不同與多執行緒所致。工具不會把任務 CPU 直接相加當成系統總和。

### 為什麼顯示「未識別裝置」？

缺 `ref.txt` 或舊版 ref 沒有裝置名稱。可在「裝置」頁設別名。

### 為什麼同一個時間點有重複樣本？

記錄器在部分秒數重複寫入。圖表取平均、統計用原始樣本，避免峰值被平均掉。

### 記憶體成長會誤報嗎？

- 時長不足觀察秒數（預設 300 秒）不會判斷
- 斜率門檻（預設 20 MB/min）可調高
- 短場次樣本少，回歸容易偏差，因此設有最短觀察時間

### 為什麼沒有 GPU 使用率？

記錄器目前只有「模擬影像緩衝 (MB)」，沒有 GPU 使用率／溫度。此為資料限制。

### 基準與 Δ 值顯示「—」？

- 尚未設定基準，或該裝置沒有基準
- 比較頁可另外自選全域基準

### 改了設定，HTML 報告沒變？

- 儲存設定後會重新分析；請**重新匯出**報告
- CLI 請用相同的 `--metadata-dir`

### 門檻太敏感／太寬鬆？

到「設定」頁調整，儲存後會立即重新分析。

### 單檔 exe 啟動較慢？

第一次啟動需解壓原生函式庫，之後較快。

## 17. 術語表

| 名詞 | 說明 |
|---|---|
| 場次 | 一次監測／記錄（一個資料夾） |
| 樣本 | 每秒一筆的量測資料 |
| 任務 | 被監控的處理程序（例如 `consumables_benchmark`） |
| 執行區間 | 任務連續「執行中」的一段時間 |
| 重啟 | 任務 PID 改變，視為重新啟動 |
| 基準（Baseline） | 用來比較的參考場次 |
| Δ 值 | 與基準的差異 |
| p50／p95 | 第 50／95 百分位數 |
| 資料完整率 | 實際樣本 ÷ 預期樣本 |
| 指紋 | 用硬體與裝置名稱計算的識別碼 |
| 中繼資料 | 存放別名／基準／備註的 `session.json` |
| LTTB | 圖表降採樣演算法，保留峰值趨勢 |
| 模擬器 CPU | 模擬器程序的 CPU 使用率 |
| 影像緩衝 | 模擬影像暫存大小（非 GPU 使用率） |
